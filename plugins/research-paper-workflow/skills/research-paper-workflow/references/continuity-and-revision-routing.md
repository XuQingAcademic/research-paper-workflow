# Conditional continuity, revision and prompt maintenance

Read only for the matching long/resumed, feedback/revision, continuous-cycle or
prompt-adaptation task. These conditions are not additional steps for a bounded
question or single specialist edit. Preserve the active objective, authorization
and existing authoritative state when this mode applies.

For a long/resumed project, accumulated experience or repeated failure, use
[goal-and-learning.md](goal-and-learning.md): recover the requested
outcome, identify its current bottleneck, and choose an action that resolves it.
Keep experience conditional on its actual evidence; correct disputed guidance
and its affected consumers, not the whole project. Use the lightest sufficient
process without weakening scientific checks. At a consequential result-to-claim
handoff or failed attempt, use the same reference to distinguish an execution
defect, inadequate evidence and a scientific contradiction before choosing a
repair or a change of direction. A local edit does not activate a
full revision cycle, and activity counts do not establish research progress.

For a consequential investment boundary or material change to the contribution
case, read [strategic-review.md](strategic-review.md). Decide whether to continue,
pivot route, park or stop using the existing evidence and design authority.
Do not let a frozen local issue queue force indefinite repair of a defeated
research route; suspend affected dependents with the existing controller's
evidence-bound `strategy-hold`, without bypassing single-active scope, inventing
an author gate or silently changing the research contract. Unaffected work outside
the held cycle remains available. Ordinary strategic notes need no controller.

For requested prompt/model optimization or a repeated evidenced execution
failure, use [prompt-trials.md](prompt-trials.md). Reuse the manager's
real-task evaluations; adapt execution to the measured model/task scope and
retain a profile only after substantive paired benefit without scientific
regression. Unknown or tied evidence keeps the configured baseline. This is
conditional maintenance, not another benchmark for every paper task.
Reuse an existing profile only within its current tested scope; without one,
continue the ordinary configured route rather than block work or invent a profile.

Treat a request that jointly changes assumptions or proof scope, notation or
terminology, and main-text/appendix presentation as a coordinated theory
revision, even when it concerns one paper section. Route an isolated theorem,
simulation, or prose edit directly to its specialist; use this workflow when
several specialist-owned artifacts must remain synchronized.

Read [stage-playbook.md](stage-playbook.md) for the next relevant
stages and [handoffs-and-state.md](handoffs-and-state.md) for every
multi-stage project. Use [portfolio-routing.md](portfolio-routing.md)
to resolve ownership. Load each selected skill's actual `SKILL.md` and required
references before invoking it. Installed availability and current project
instructions outrank this dated inventory.

When feedback accumulates, the research target changes, or work resumes across
stages, read [feedback-and-decisions.md](feedback-and-decisions.md).
Reuse the project's existing feedback and decision records; distinguish advice
collected from changes authorized, implemented and checked. Carry forward a short
current-state summary derived from those records, not a competing claims ledger.
When the existing records have explicit structured fields, use the read-only
[resume-view.md](resume-view.md) adapter to rebuild that summary and
check whether a saved view is stale. Unmapped prose still needs source reading;
a generated view cannot authorize work or settle scientific questions.
Read the latest scoped author decisions and reviews before consuming an older
recommendation or handoff. A read-only review need not rewrite old artifacts;
at authorized continuation reconcile its evidence with the old decision before
using that decision to justify new work. See the same feedback reference for
producer-version and source/PDF/package mismatches.

For iterative paper optimization, use
[iterative-optimization.md](iterative-optimization.md). A cycle can
contain several issues from eight optional areas; execute one selected issue at
a time, including its necessary dependent edits. There is no fixed three-round
count or theory/notation/writing order. Preserve whether the user requested one
item or continuous completion of the selected cycle; do not turn serial work
into repeated approval stops or parallel edits to unrelated issues.
Keep the frozen objective above the local issue queue; apply the bottleneck and
admission guidance in the goal reference and iterative playbook, rather than
continuing in the vocabulary or formatting neighborhood of the last edit.
For every material cycle, also read
[non-regression-contract.md](non-regression-contract.md) and define
what must improve, what must not regress, bounded trade-offs, paired evidence,
rollback conditions, and final whole-candidate review dimensions. Keep this
lightweight in ordinary single-item work and machine-checkable in continuous
revision. This contract supports a bounded non-regression claim; it does not
promise that every paper dimension improves.
When an active issue changes assumptions, theorem statements, proofs, notation,
or theory exposition, also read
[theory-revision-contract.md](theory-revision-contract.md). Keep the
complete verification derivation and the concise manuscript presentation as
synchronized views of the same result; freeze any author-selected literature and
notation priority at the project level rather than turning it into a global rule.
Newly initialized continuous cycles also enforce the v2 issue package's
objective-link and admission fields; legacy v1 cycle state remains readable for
project continuity.

When the user requests one-start autonomous revision through an author-reviewable
candidate, also read [continuous-revision.md](continuous-revision.md).
Freeze its project contract, keep `.paper/revisions.yaml` as the issue authority,
and use `scripts/revision_cycle.py` for the single-active queue, hash-bound
reviews, author pauses and convergence checks. New cycles require
`paper-revision-contract.v2`; its current non-regression report is a readiness
gate, and accepted full reviews bind both the manuscript and that report. Legacy
v1 cycles remain readable but do not gain a retroactive machine-enforced report.
Continuous mode does not authorize
named experts, new compute, external access or submission; those must be present
in the frozen contract and remain subject to their own skills and permissions.
